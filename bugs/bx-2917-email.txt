Root-cause fix — verify the container, not just the blob. Replace the whole-tree scan with positional selection inside a validated multipart/signed:

Require msg.get_content_type() == 'multipart/signed' at the top level.
Require exactly two body parts. Reject three or more (this is what kills variant 2) and reject a nested or repackaged structure (variant 1).
Require the protocol parameter of the top-level Content-Type to equal the second part's content type (application/x-pkcs7-signature or application/pkcs7-signature), and require micalg to match the digest algorithm named in the CMS SignedData. Reject on mismatch.
Take part index 0 as the signed content and part index 1 as the signature. Do not search by content type; do not accept text/plain from anywhere else in the tree. Preserve the signed part's exact transfer-encoded octets rather than re-deriving them, so no canonicalisation ambiguity remains.
Defence in depth — change the API so the scope is not lost. Return the verified content bytes (and the signer certificate) alongside the booleans, for example a result object exposing signed_bytes, so a caller can display exactly what was covered and nothing else. Keep the current signature as a thin, documented wrapper if backwards compatibility is required, but mark it as unable to express which bytes were signed. Note that endesive/plain/verify.py is already immune by construction, because the caller passes the signed octets explicitly rather than letting the library guess them from a document — that is exactly the shape the mail verifier should adopt.

Data migration — none is required, no stored state is affected. However, any archived "signature verified" verdict produced by an affected version is unreliable, because a message accepted then would be accepted for content that was never signed. Deployments that persist verification outcomes for compliance should re-verify their archive with a fixed version, or with openssl smime -verify, which already rejects both variants.
